# Architecture decisions v1.1

Продолжение ADR-001…010 из `architecture-v1/09_DECISIONS.md`. Здесь фиксируется, что изменилось при переходе от спецификации к работающему коду.

## ADR-011: Rules-first вместо callable Cloud Functions (MVP) — Accepted
**Контекст.** Cloud Functions можно задеплоить только на тарифе Blaze (с картой). План v1 полностью держался на callable-функциях, асинхронном воркере, очереди `dirtySummaries`, квитанциях `operationReceipts` и CAS-проекциях.
**Решение.** Преподаватель пишет канонические записи напрямую в Firestore, все инварианты проверяют Security Rules:
- права через `offering.staffUids`, зачисление через `offering.studentUids` (записывает только админ/seed);
- `revision == старая + 1`: оптимистичная блокировка прямо в правилах;
- `updatedBy == auth.uid`, `updatedAt == request.time`: нельзя подделать автора и время;
- баллы в `[0, max]`, у `unmarked` и `pending` баллов нет;
- изменение опубликованного значения требует `correction.reason`.

Идемпотентность получается сама собой: ID записи детерминированный (`{sessionId}_{studentUid}`), повтор перезаписывает тот же документ, а ревизия отсекает устаревшие записи.
**Что заменяет.** ADR-003 (server-only writes) и ADR-006 (проекции) на время MVP.
**Цена.** Сложные межсущностные проверки ограничены бюджетом правил: ≤ 20 обращений к документам на коммит. Поэтому клиент пишет по 8 записей на коммит. Нет серверных push-уведомлений.
**Пересмотр.** При переходе на Blaze команды переезжают в функции за тем же интерфейсом `@aitu/data`. Модель данных не меняется.

## ADR-012: Risk Engine считается на клиенте общим модулем — Accepted
Студент читает только **свои опубликованные** записи и считает риск модулем `@aitu/domain`. Тот же модуль показывает преподавателю радар группы. Расчёт детерминированный, поэтому оба видят одно и то же. Подделать свой риск можно только на собственном экране, вреда в этом нет. Если понадобятся серверные сводки или уведомления, `shouldApplyProjection` уже лежит в домене.

## ADR-013: Одна запись на (оценивание, студент) с независимыми полями — Accepted
`assessmentRecords/{assessmentId}_{studentUid}` хранит `submission` (сдано / не сдано / …) и `gradeState` + `points` (проверено / нет). Семантика v1 сохранена: это независимые состояния, а просрочка считается только по явному `submission = missing` после дедлайна. Отдельные коллекции `taskCompletionRecords` и `gradeRecords` удвоили бы интерфейс и количество записей ради флага публикации, который на практике общий.

## ADR-014: Денормализованные `staffUids` / `studentUids` в offering — Accepted
Чтобы правило проверяло членство за один `get()`, а запросы `array-contains` были доказуемо ограничены пользователем. Документы `enrollments/{uid}` остаются источником имён и статусов. Seed поддерживает обе стороны согласованными. Компромисс: зачисленный студент видит непрозрачные UID однокурсников (имён и оценок не видит).

## ADR-015: TypeScript для нового кода — Accepted
Пересматривает ADR-009. Пакеты `domain` и `data` и Teacher Portal написаны на strict TS (`noUncheckedIndexedAccess`, `erasableSyntaxOnly`), поэтому доменные тесты запускаются в Node без сборки. My DU переводится на TS постепенно, при миграции.

## ADR-016: Честные метрики вместо «72/100» и «среднего по классу» — Accepted
Общий балл не определён ни в одной политике AITU, а среднее по классу требует чтения чужих оценок. Вместо них:
- `summarizeRadar()`: число курсов в каждом состоянии и «фокус-курс»;
- сравнение с порогом цели;
- динамика только по опубликованным оценкам.

## ADR-017: Облачный демо-проект — основной режим, эмулятор — для тестов — Accepted
**Контекст.** Систему нужно показывать преподавателю: открыть портал с любого устройства и посмотреть саму базу. При этом не требовать Java на ноутбуке разработчика.
**Решение.** Один проект Firebase на Spark: Auth (Email/Password), Firestore, Hosting. Конфигурация лежит в корневом `.env` и общая для портала (Vite `envDir` + `envPrefix`) и скриптов (`process.loadEnvFile`). Правило выбора режима — `resolveFirebaseConfig()`: есть `FIREBASE_PROJECT_ID` → облако, иначе эмулятор. Seed пишет в облако через Admin SDK с ключом сервисного аккаунта и только с явным `--yes`. Deploy — кроссплатформенный `scripts/deploy.ts`.
**Безопасность.** Web-конфиг не секретный, доступ защищают Security Rules. Ключ сервисного аккаунта секретный и хранится вне репозитория. Демо-пароли публичные, поэтому в проекте только синтетические данные (ADR-010). Преподаватель получает роль Viewer в консоли.
**Пересмотр.** Перед реальными данными нужны отдельные проекты `dev` и `prod`, App Check, budget alert и отказ от публичных демо-паролей.

## ADR-018: Оба приложения на одном Hosting-сайте — Accepted
Портал лежит в `/`, My DU в `/my-du/` (`dist/hosting`, rewrites в `firebase.json`). Один домен, один деплой, без второго сайта в консоли. My DU собирается с `base: './'`, поэтому не зависит от пути. Service worker ограничен своей областью `/my-du/`, а `index.html` и `sw.js` отдаются с `no-cache`, чтобы новый деплой подхватывался сразу.

## ADR-019: Демо-база v2 — Accepted
2 группы × 25 студентов, 5 курсов, 4 преподавателя, ≈4 900 документов: четверть дневной квоты записи Spark, поэтому seed можно запускать несколько раз в день. Генератор чистый и детерминированный (`scripts/seed-data.ts`). `verify-seed` проверяет:
- контракт полей с правилами;
- сценарии Армана;
- что встречаются все четыре состояния риска;
- что большинство студентов «в норме» (реалистичная, а не пугающая картина).

## ADR-020: Оценивание по правилам AITU вместо демо-порога оценок — Accepted
Сигнал «последние оценки ниже 60 %» заменён моделью AITU (`risk-aitu-v1`): Register Midterm/Endterm с весами из силлабуса, RegTerm, допуск (25 / 25 / 50), Total = 0.3/0.3/0.4, FX/F, стипендия ≥ 70 % по курсу.
- Новые причины: `ADMISSION_RISK` (одна даёт High — это прямой путь к F) и `SCHOLARSHIP_RISK`. Новые действия `RAISE_REGISTER`, `PROTECT_SCHOLARSHIP` содержат расчёт «сколько нужно».
- Курс без периодов у оцениваний работает по-старому (`RECENT_GRADES_LOW`), поэтому модель обратно совместима.
- Регистры вычисляются, а не хранятся (единый расчёт у преподавателя и студента).
- **Пересмотр:** веса и пороги должны совпадать с официальным силлабусом и академической политикой AITU; сейчас взяты со скриншотов Moodle и слов пользователя.

## ADR-021: Каталог аудиторий в коде — Accepted
Список аудиторий небольшой и меняется редко, поэтому он лежит в `@aitu/domain` и не тратит чтения Firestore. Поле `room` остаётся строкой, правила его не проверяют по каталогу (свободный ввод разрешён для нестандартных мест). Поиск понимает кириллическую «С», пробелы и регистр; при вводе `C1.` фильтрует по корпусу, предпочитает тип под формат занятия (лекция → L, практика → P, лаба → K).

## ADR-022: Демо-база v3 — Accepted
Семестр AITU: неделя 8 из 15, занятия недель 1–10, Quiz 1 (нед. 3), Midterm (нед. 5), Quiz 2 (нед. 8, в Calculus — черновик), Endterm (нед. 10), Final (нед. 12). ≈6 300 документов. Распределение риска по всем курсам: High 13 %, Medium 23 %, Low 54 %, Unknown 10 %.

## ADR-023: Адаптивность Teacher Portal без отдельной мобильной версии — Accepted
Один набор компонентов, три контрольные точки: 1100 px (скрывается боковая панель), 860 px, 640 px (телефон). На телефоне таблицы-«листы» (посещаемость, оценки, занятия) перестраиваются CSS-гридом в карточки — разметка таблицы и доступность (role, aria-label) не меняются. Широкие отчёты (журнал оценок, радар, участники) остаются таблицами и прокручиваются внутри `.table-wrap`. Причина горизонтального скролла страницы на ноутбуке — sticky-ячейки журнала выходили за `overflow: auto`; исправлено `contain: paint` на обёртке.

## ADR-024: Офлайн-адаптер Firebase для демонстрации — Accepted
`tools/offline/*` реализует используемое подмножество `firebase/app|auth|firestore` в памяти (seed из `scripts/seed-data.ts`, изменения в localStorage, синхронизация вкладок через BroadcastChannel). Подключается только `vite --mode offline`. Это резервный вариант для защиты без сети и для записи видео; Security Rules в нём не проверяются, поэтому безопасность показывается только на реальном проекте.

## ADR-025: Медиа-конвейер и правовая чистота ассетов — Accepted
Растровые картинки хранятся в WebP при 2× от CSS-размера (`scripts/optimize-media.mjs`), иконки приложения — PNG (требование iOS/PWA). Реальное фото и маркетинговые фото AITU удалены; бренд-ассеты AITU (логотип, маскот Дью, иконка) помечены © AITU и используются только в учебном прототипе.

## ADR-026: Три роли, роль администратора — в токене — Accepted (v1.0)
- **Студент** регистрируется сам (`users/{uid}` с `role: 'student'`, `source: 'self'`). Правила проверяют каждое поле: роль принудительно `student`, почта совпадает с почтой из токена и корпоративная (`@astanait.edu.kz`, демо — `@demo.aitu.kz`), ФИО, группа `SE-2419`, номер 5–10 цифр, направление из списка, согласие и время — серверные.
- **Преподавателя** создаёт только администратор: аккаунт Auth создаётся из второго экземпляра Firebase-приложения (иначе администратор вышел бы из своей сессии), пароль временный (14 символов, показывается один раз), `mustChangePassword: true` → портал не пускает дальше страницы смены пароля.
- **Администратор** — custom claim `admin: true`, его ставит только Admin SDK (`npm run make-admin`). Поле `role: 'admin'` в документе ничего не даёт: правила смотрят в токен (`request.auth.token.admin`). Так роль нельзя присвоить себе ни из браузера, ни правкой документа.
- Отвергнуто: Cloud Functions для создания аккаунтов (нужен тариф Blaze); вход через Microsoft Entra ID (нужно разрешение AITU, см. обсуждение — отложено).

## ADR-027: Вступление в курс по коду — Accepted (v1.0)
Код из 6 символов алфавита без похожих знаков (`ABCDEFGHJKMNPQRSTUVWXYZ23456789`, 31⁶ ≈ 887 млн вариантов), показывается как `XXX-XXX`. `joinCodes/{code}` читается только по точному коду (`get`), список закрыт (`list` — только администратор), поэтому коды нельзя перебрать запросом. Документ хранит «превью» (курс, группа, семестр) — студент видит, КУДА вступает, до вступления; правила требуют, чтобы превью совпадало с курсом (`getAfter`).
Вступление — одна атомарная пачка: `offering.studentUids += self` + `enrollments/{self}` с `joinCode`. Правила проверяют, что добавлен ровно сам студент, курс активен, код активен и открывает именно этот курс, данные зачисления скопированы из настоящего профиля, почта подтверждена (ADR-030). Смена кода сразу отключает старый (`active: false`), уже вступившие остаются.

## ADR-028: QR-отметка у двери (IoT) — Accepted (v1.0)
«Устройство» — браузер на планшете у двери (`/door/{offering}/{session}`). Каждые 20 с он записывает в `checkinTokens/{session}` новый 6-значный код и `rotatedAt == request.time`. Студент отправляет `checkins/{session}_{uid}`; правило принимает, если он зачислен, отметка открыта, код равен текущему или предыдущему и `request.time < rotatedAt + 45 s` — **время сервера**, часы телефона не важны. Фото QR, пересланное в чат, перестаёт работать меньше чем через минуту. Документ отметки создаётся один раз (id = сессия + студент), изменить или удалить его нельзя.
QR-отметка — **подсказка**, а не оценка посещаемости: преподаватель переносит её в ведомость (`present`, позже 10 минут — `late`, примечание «QR 11:51») и публикует как обычно. Поэтому ошибка устройства не портит журнал.
Экран у двери показывает только число отметившихся (экран смотрит в коридор). `npm run iot:simulate` — симулятор датчика через Admin SDK для демонстрации без телефонов.

## ADR-029: Резервное копирование без тарифа Blaze — Accepted (v1.0)
Управляемый экспорт Firestore требует Blaze, поэтому копия — это JSON всех документов (Timestamps как `{"__ts": ms}`): из панели администратора (клиентское чтение по правам администратора), `npm run backup` и ночной GitHub Actions (Admin SDK). Восстановление — только `npm run restore` с компьютера владельца: по умолчанию пробный прогон, `--yes` для записи, `--wipe` для полного отката. Пароли в копию не входят (их хранит Firebase Auth), личные галочки плана студентов — тоже (не критичны и приватны). В браузере есть проверка файла копии, которая ничего не отправляет на сервер.

## ADR-030: Подтверждение почты перед вступлением в курс — Accepted (v1.0)
Регистрация по паролю не доказывает, что человек владеет ящиком: можно зарегистрироваться на чужую корпоративную почту. Поэтому вступать в курсы может только аккаунт с `email_verified` (письмо отправляется при регистрации, в My DU — «Я подтвердил(а)» и «Отправить ещё раз»). Исключение — демо-домен `@demo.aitu.kz` (ящиков не существует): такие аккаунты могут вступать **только в демо-курсы** (`demo-*`), но не в настоящие.

## ADR-031: Статистика по запросу, а не на каждое открытие — Accepted (v1.0)
Аналитика по всем курсам читает всю базу (≈6 000 документов ≈ 12 % дневной квоты чтения Spark). Поэтому её пересчитывают кнопкой «Пересчитать», а результат кэшируется в `stats/latest` для всех администраторов. Считаются только опубликованные записи, как у студентов. Графики: одна величина на график, без двойных осей, у каждого есть табличный вид; цвета риска всегда с подписью.

## ADR-032: Заголовки безопасности и сессия — Accepted (v1.0)
`firebase.json` задаёт CSP (скрипты только свои, подключения только к Firebase, `frame-ancestors 'none'`, `object-src 'none'`), HSTS, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` (камера/микрофон/геолокация выключены: QR сканирует системная камера телефона, а не страница) и COOP. Портал выходит из аккаунта после 30 минут бездействия (общие компьютеры в аудиториях). Подробно — `docs/SECURITY.md`.
